# 서포터즈 제보 관리 대시보드 기획서

## 1. 프로젝트 개요

서포터즈 제보 관리 대시보드는 서포터즈가 전달한 이슈 제보를 운영 데이터로 등록하고, 등록된 제보를 기간/서비스/플랫폼/상태 기준으로 조회·분석하는 내부 운영툴입니다.

초기에는 프론트엔드 목업 데이터 기반으로 시작했지만, 현재는 Supabase를 원격 저장소로 사용하여 여러 컴퓨터에서 동일한 제보 데이터를 조회할 수 있도록 구성했습니다.

## 2. 프로젝트 목표

- 서포터즈 제보 내용을 표준화된 항목으로 등록한다.
- 등록된 제보를 이슈 리스트에서 검색, 필터링, 상세 확인, 수정, 삭제할 수 있게 한다.
- 대시보드에서 월별, 작성자별, 서비스별, 이슈 아님 사유별 현황을 확인한다.
- 배포 환경에서도 Supabase 기반으로 동일 데이터를 공유한다.
- 관리자용 내부 운영툴에 어울리는 간결하고 명확한 UI를 제공한다.

## 4. 화면 구성

서비스는 총 3개 주요 화면으로 구성됩니다.

| 화면 | 경로 | 목적 |
| --- | --- | --- |
| 대시보드 | `/dashboard` | 제보/이슈 현황 분석 |
| 이슈 입력 | `/issues/new` | 신규 제보 등록 |
| 이슈 리스트 | `/issues` | 제보 목록 조회, 상세 확인, 수정, 삭제 |

## 5. 공통 레이아웃

상단 내비게이션 바는 모든 화면에서 공통으로 사용됩니다.

- 좌측: 서비스명 `서포터즈 제보 관리`
- 중앙 메뉴: `대시보드`, `이슈 입력`, `이슈 리스트`
- 우측: 관리자 프로필 영역
- 본문 영역은 관리자용 내부 운영툴 느낌의 밝은 배경과 카드/테이블 기반 UI로 구성

## 6. 기간 정책

기간은 운영 연도 기준의 1년 단위로 관리합니다.

예시:

- `2025.04.01 - 2026.03.30`
- `2026.04.01 - 2027.03.30`

대시보드에서는 기간을 1년 단위로만 조회하는 방향을 기준으로 설계했습니다. 이슈 리스트는 검색 목적이 강하므로 기간 시작일/종료일 필터를 유지할 수 있습니다.

- 실행 경로 불명확

### 7.5 주요 동작

- `이슈 아님` 선택 시 `수정 여부`는 비활성화되며 `-`로 저장됩니다.
- `이슈 아님`이 아닐 때는 `이슈 아님 사유`가 비활성화됩니다.
- 등록 시 Supabase `supporter_issues` 테이블에 저장됩니다.
- 임시 저장은 브라우저 localStorage에 저장하지 않고 콘솔 로그와 안내 메시지만 제공합니다.

## 9. 대시보드 화면

### 9.1 필터

- 기간
- 서비스
- 플랫폼
- 이슈 여부
- 수정 여부

### 9.2 KPI 카드

- 전체 제보 수
- 전체 이슈 수
- 수정 완료 수
- 개선율
- 이슈 아님 수

개선율 계산식:

```text
수정 완료 수 / 전체 이슈 수 * 100
```

전체 이슈 수가 0인 경우 개선율은 0%로 처리합니다.

### 9.3 월별 현황

월별 현황 차트는 다음 지표를 표시합니다.

- 제보 이슈 수
- 서비스 전달 이슈 수
- 수정 이슈 수

각 지표 기준:

| 지표 | 기준 |
| --- | --- |
| 제보 이슈 수 | 이슈 여부가 `이슈`인 건수 |
| 서비스 전달 이슈 수 | 서비스 전달 Jira 링크가 있는 건수 |
| 수정 이슈 수 | 이슈 여부가 `이슈`이고 수정 여부가 `수정 완료`인 건수 |

### 9.4 작성자별 제보 현황

작성자별로 다음 수치를 확인합니다.

- 전체 제보
- 이슈
- 이슈 아님
- 수정 완료

### 9.5 서비스별 현황

서비스별 현황은 이슈가 생성된 서비스만 표시합니다.

- 전체 제보
- 이슈
- 수정 완료
- 개선율

### 9.6 이슈 아님 분석

이슈 아님 사유별 건수를 차트와 테이블로 확인합니다.

## 11. 저장 방식

현재 이슈 데이터는 브라우저 localStorage에 저장하지 않습니다.

저장 흐름:

1. 사용자가 이슈 입력 화면에서 등록
2. React 상태에 즉시 반영
3. Supabase REST API로 `supporter_issues` 테이블에 저장
4. 다른 컴퓨터에서 접속 시 Supabase에서 동일 데이터 조회

필수 환경변수:

```bash
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_xxxxx
```

로컬 개발에서는 `.env.local`, Vercel 배포에서는 Vercel Environment Variables에 등록해야 합니다.

## 12. 배포

현재 Vercel 배포를 기준으로 구성되어 있습니다.

Vercel 설정:

- Framework Preset: Vite
- Build Command: `npm run build`
- Output Directory: `dist`
- SPA 새로고침 대응: `vercel.json` routes fallback 사용

환경변수는 Production 환경에 반드시 등록해야 합니다.

## 13. 운영 시 유의사항

- Supabase publishable key만 프론트엔드에 사용합니다.
- `sb_secret_...` 키는 절대 브라우저 앱에 넣지 않습니다.
- 현재 Supabase RLS 정책은 내부 운영툴 빠른 사용을 위한 공개 읽기/쓰기 예시입니다.
- 실제 운영 보안 강화를 위해서는 Supabase Auth를 도입하고 관리자 권한 기반 정책으로 좁히는 것이 좋습니다.
