# 서포터즈 제보 관리 대시보드 기획서

## 1. 프로젝트 개요

서포터즈 제보 관리 대시보드는 서포터즈 활동 중 생성된 이슈를 등록하고, 등록된 데이터를 기간/서비스/플랫폼/상태/유형 기준으로 조회·분석하는 내부 운영툴입니다.

초기에는 프론트엔드 목업 데이터 기반으로 시작했지만, 현재는 Supabase를 원격 저장소로 사용하여 여러 컴퓨터에서 동일한 제보 데이터를 조회하고 관리할 수 있도록 구성했습니다.

## 2. 프로젝트 목표

- 서포터즈 제보 내용을 표준화된 항목으로 등록한다.
- 등록된 제보를 이슈 리스트에서 검색, 필터링, 상세 확인, 수정, 삭제할 수 있게 한다.
- 대시보드에서 핵심 지표, 월별 현황, 작성자별 현황, 서비스별 현황, 유형별 현황을 확인한다.
- 월별 리포트에서 월 단위 제보/전달/수정 현황과 1차·2차 전달 건수를 확인한다.
- Supabase 기반으로 배포 환경에서도 동일한 데이터를 공유한다.
- 라이트 모드와 다크 모드를 모두 지원하고, 저시력 사용자도 구분하기 쉬운 UI를 제공한다.

## 4. 화면 구성

서비스는 총 4개 주요 화면으로 구성됩니다.

| 화면 | 경로 | 목적 |
| --- | --- | --- |
| 대시보드 | `/dashboard` | 핵심 지표와 이슈 현황 분석 |
| 월별 리포트 | `/reports/monthly` | 월별 제보/전달/수정 현황 확인 |
| 이슈 리스트 | `/issues` | 제보 목록 조회, 검색, 필터링, 상세 확인, 수정, 삭제 |
| 이슈 입력 | `/issues/new` | 신규 제보 등록 |

## 5. 공통 레이아웃

상단 내비게이션 바는 모든 화면에서 공통으로 사용됩니다.

- 좌측: 서비스명 `서포터즈 제보 관리`
- 중앙 메뉴: `대시보드`, `월별 리포트`, `이슈 리스트`, `이슈 입력`
- 우측: 라이트/다크 모드 전환 버튼
- 본문 영역은 내부 운영툴에 맞게 카드, 테이블, 필터 패널 중심으로 구성

## 6. 기간 정책

기간은 운영 연도 기준의 1년 단위로 관리합니다.

예시:

- `2025.04.01 - 2026.03.30`
- `2026.04.01 - 2027.03.30`

대시보드와 이슈 리스트에서는 시작일/종료일을 직접 조정할 수 있습니다. 대시보드에서 유형별 건수 링크를 통해 이슈 리스트로 이동할 때는 현재 선택한 기간이 함께 전달되어 동일한 조건으로 목록을 확인할 수 있습니다.

### 7.5 주요 동작

- `이슈 아님`이 아닐 때는 `이슈 아님 사유`가 비활성화됩니다.
- 서비스 전달 링크는 여러 개를 추가할 수 있습니다.
- 등록 시 Supabase `supporter_issues` 테이블에 저장됩니다.
- 등록 성공 메시지는 라이트/다크 모드 모두에서 명도 대비를 고려해 표시됩니다.

### 8.3 목록 테이블

| 컬럼 | 설명 |
| --- | --- |
| 등록일 | 제보 등록일 |
| 작성자 | 작성자 이름 |
| 서비스 | 서비스명 |
| 플랫폼 | 플랫폼 |

### 8.4 상세 모달

상세 모달에서는 제보 내용을 확인하고 다음 작업을 수행할 수 있습니다.

- 상세 보기
- 수정
- 복사
- 삭제
- Jira 링크 외부 이동

Jira 링크는 `서포터즈`와 `서비스 전달`을 구분해서 표시합니다. 서비스 전달 링크가 여러 개인 경우에도 줄바꿈과 정렬이 깨지지 않도록 구성되어 있습니다.

## 9. 대시보드 화면

### 9.1 필터

- 기간
- 서비스
- 플랫폼
- 이슈 여부
- 수정 여부

대시보드 필터 하단에는 서포터즈 구글시트 바로가기 링크를 제공합니다.

- 1기 구글시트
- 2기 구글시트
- 3기 구글시트

### 9.2 KPI 카드

대시보드 핵심 지표는 다음 순서로 표시합니다.

| 지표 | 설명 |
| --- | --- |
| 서포터즈 이슈 | 서포터즈 스프린트 내 생성된 건수 |
| 이슈 아님 | 검토 후 이슈 아님으로 판정된 건수 |
| 최종 전달 건수 | 아지트 및 서비스팀에 전달된 건수 |
| 수정 완료 | 전달 이슈 중 수정이 완료된 건수 |
| 수정 불가 | 전달 이슈 중 수정이 불가한 건수 |
| 개선율 | 최종 전달 이슈 중 수정 완료 비율 |

개선율 계산식:

```text
수정 완료 수 / 최종 전달 건수 * 100
```

최종 전달 건수가 0건인 경우 개선율은 0%로 처리합니다.

### 9.3 집계 기준 모달

대시보드에는 지표 산정 기준을 확인할 수 있는 안내 모달이 있습니다.

모달에서는 다음 기준을 설명합니다.

- 서포터즈 이슈
- 이슈 아님
- 최종 전달 건수
- 수정 완료
- 수정 불가
- 개선율

서포터즈 이슈 수와 최종 전달 건수가 1:1로 일치하지 않을 수 있는 이유도 함께 안내합니다. 하나의 서포터즈 이슈가 여러 서비스팀 이슈로 분리 전달될 수 있기 때문입니다.

### 9.4 월별 현황 차트

월별 현황 차트는 다음 지표를 표시합니다.

- 서포터즈 이슈
- 수정 완료
- 최종 전달 건수

차트 툴팁과 범례에서도 동일한 용어를 사용하며, 수치 뒤에는 `건`을 붙여 표시합니다.

### 9.5 작성자별 제보 현황

작성자별 제보 현황은 다음 수치를 표시합니다.

- 제보 수
- 이슈 아님
- 최종 전달 건수

작성자명 뒤에 `_숫자`가 붙은 중복 표기 계정은 작성자 집계에서 보정하여 표시합니다.

### 9.6 서비스별 현황

서비스별 현황은 이슈가 생성되었거나 전달/수정 데이터가 있는 서비스만 표시합니다.

- 서비스
- 서포터즈 제보 이슈 수
- 접근성 이슈 수
- 수정된 이슈 수
- 이슈 아님 수
- 수정 불가 이슈 수

테이블의 칸 비율은 동일하게 맞추고, 서비스명은 가운데 정렬합니다.

### 9.7 유형별 건수

이슈 아님 사유별 건수를 차트와 테이블로 확인합니다.

테이블의 유형 텍스트를 선택하면 이슈 리스트로 이동하며, 해당 이슈 아님 사유와 현재 대시보드 기간이 필터로 적용됩니다.

## 10. 월별 리포트 화면

### 10.1 목적

월별 리포트는 운영 기간 내 월별 제보, 전달, 수정 현황을 표 형태로 확인하는 화면입니다.

### 10.2 KPI 카드

- 서포터즈 이슈
- 이슈 아님
- 최종 전달 건수
- 수정 완료
- 수정 불가

대시보드와 동일한 카드 디자인과 지표 순서를 사용합니다.

### 10.3 월별 운영 리포트

월별 테이블은 다음 컬럼으로 구성됩니다.

| 컬럼 | 설명 |
| --- | --- |
| 해당 월 | 월 |
| 서포터즈 이슈 | 해당 월에 생성된 서포터즈 이슈 |
| 최종 전달 이슈 | 최종 전달된 이슈 |
| 이슈 아님 | 이슈 아님으로 판정된 건 |
| 수정 완료 이슈 | 수정 완료된 전달 이슈 |
| 수정 불가 이슈 | 수정 불가로 판정된 전달 이슈 |

각 수치 아래에는 1차·2차 전달 구간별 건수를 함께 표시합니다.

- 1차: 매월 1일 - 15일
- 2차: 매월 16일 - 말일

## 11. 데이터 모델

### 11.1 TypeScript 타입

```ts
type IssueItem = {
  id: string;
  registeredAt: string;
  authorName: string;
  serviceName: string;
  platform: string;
  path: string;
  issueStatus: "이슈" | "이슈 아님" | "보류";
  fixStatus: "-" | "수정 필요" | "수정 완료" | "수정 불가";
  notIssueReason?: string;
  jiraKey?: string;
  supporterJiraUrl?: string;
  serviceJiraUrl?: string;
  memo?: string;

```

서비스 전달 링크는 화면에서는 여러 개의 입력 필드로 관리하고, 저장 시 하나의 문자열 필드로 정규화해 저장합니다.

### 11.2 Supabase 테이블

테이블명:

```text
supporter_issues
```

주요 컬럼:

- id

- platform
- path
- issue_status
- fix_status
- not_issue_reason
- jira_key
- supporter_jira_url
- service_jira_url
- memo
- created_at
- updated_at

## 12. 저장 방식

현재 이슈 데이터는 브라우저 localStorage에 저장하지 않습니다.

저장 흐름:

1. 사용자가 이슈 입력 화면에서 등록
2. React 상태에 즉시 반영
3. Supabase REST API로 `supporter_issues` 테이블에 저장
4. 다른 컴퓨터에서 접속 시 Supabase에서 동일 데이터 조회

필수 환경변수:

```bash
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_xxxxx
```

로컬 개발에서는 `.env.local`, 배포 환경에서는 배포 서비스의 Environment Variables에 등록해야 합니다.

## 14. 접근성 및 디자인 정책

- 라이트 모드와 다크 모드를 모두 지원합니다.
- 상태 배지, KPI 아이콘, 페이지네이션은 색상만으로 구분하지 않고 텍스트와 형태를 함께 사용합니다.
- 저시력 사용자를 고려해 명도 대비를 확보합니다.
- 페이지네이션은 숫자 버튼을 최대 10개까지 표시하고, 다음 버튼으로 다음 번호 구간을 확인할 수 있습니다.
- 테이블 컬럼은 정렬과 칸 비율을 맞춰 반복 조회에 적합하게 구성합니다.

## 15. 운영 시 유의사항

- Supabase publishable key만 프론트엔드에 사용합니다.
- `sb_secret_...` 키는 절대 브라우저 앱에 넣지 않습니다.
- 현재 Supabase RLS 정책은 내부 운영툴 빠른 사용을 위한 공개 읽기/쓰기 예시일 수 있습니다.
- 실제 운영 보안 강화를 위해서는 Supabase Auth를 도입하고 관리자 권한 기반 정책으로 좁히는 것이 좋습니다.
